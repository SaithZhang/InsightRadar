# 持仓管理技术方案

2026-11-09 · InsightRadar V0.02 本机版增量 · 已实现并验证

需求基线见 [持仓管理与模块规划](PRD-我的持仓.md)。本增量复用 Vue、Spring Boot 和本机 PostgreSQL。每只证券维护一份合并持仓，手工录入。用户为现有 MA55 条件选择预设动作，报告给出动作、依据和下次检查时间。交易由用户在券商端确认执行，`trade_authority` 仍为 `none`。

## 1. 页面与导航

| 顶部入口 | 地址 | 工作流 |
| --- | --- | --- |
| 持仓 | `#/positions` | 「持仓管理」默认展示持有，支持查看已清仓。可新增、编辑、确认未变和标记清仓。点证券进入个股分析，返回恢复列表筛选和位置。 |
| 个股分析 | `#/analysis?code=002463.SZ` | 沿用现有行情、K 线和公告区。首屏依次展示持仓状态、下一步动作、条件及依据。显式点击「生成分析」后提交任务，保留生产／调试选择。 |
| 分析记录 | `#/history?code=002463.SZ`、`#/history?runId=…` | 按标的、生成日期筛选已保存记录。按 run ID 打开只读报告，显示当时的持仓、规则及证据。 |

`App.vue` 保留应用外壳及顶栏，拆出三个视图，个股页与历史详情复用报告展示组件。三个固定页面用浏览器片段和 `hashchange` 切换，沿用 Vue 和现有静态入口。空片段默认进入个股分析，浏览器前进、后退和刷新可以重新定位。列表筛选和报告 ID 可写入地址，股数、成本和动作仅放在页面状态与本地 API。应用外壳保留持仓列表的滚动位置，从分析页返回时等列表渲染后恢复。桌面和窄屏都显示当前入口。打开页面、切换标的或读取历史均走查询路径。已有 D+1 检查按钮继续由用户主动触发，结果追加到原后验记录。

市场情绪、选股、量化分析、量化回测按需求文档归类，实际开放时再加入导航。首版实现这三个入口。

## 2. 持仓存储与 API

新增 Flyway `V4__positions.sql`，在本机 PostgreSQL 增加 `positions`。该表保存当前记录，分析历史继续使用现有不可变报告。

| 字段 | 约束与语义 |
| --- | --- |
| `canonical_code` | 主键，引用 `securities.canonical_code`。证券身份由本地已核验主数据或现有行情解析器确认。 |
| `quantity` | 非负整数股数，首版上限 999,999,999。正数表示持有，零表示用户确认清仓；没有记录表示未登记。 |
| `unit_cost` | 可空 `numeric(18,6)`，按用户的券商每股成本口径原样保存，允许零和负值。清仓时置空。 |
| `on_ma55_trigger` | 可空。两种预设为 `REVIEW_REDUCTION`（进入减仓评估）与 `REVIEW_EXIT`（进入退出评估）。清仓时置空，重新建仓时可重新选择。 |
| `source`、`confirmed_at`、`updated_at`、`version` | 来源固定为 `MANUAL`，时间由服务端以 UTC 存储、页面以北京时间显示。首次保存版本为 1，每次有效提交递增。 |

| 接口 | 行为 |
| --- | --- |
| `GET /api/v1/positions?status=holding\|cleared\|all` | 默认返回持有。包含已核验证券身份、持仓与确认时间、可用的本地行情及估值。查询只读 PostgreSQL。 |
| `PUT /api/v1/positions/{canonicalCode}` | 提交 `quantity`、`unitCost`、`onMa55Trigger`、`expectedVersion`。首次用版本 0，后续使用读到的版本。服务端校验股数、成本精度和动作枚举，并确认路径代码与证券身份一致。 |
| `GET /api/v1/analyses?code=&from=&to=&page=&size=` | 扩展原列表，标的与日期可选。日期过滤用北京时间生成日，起止日期均包含，SQL 使用半开区间。带后缀时按已确认 canonical code 查找，未解析任务保留请求代码；裸代码沿用按六位查找。保留原分页和已有调用。 |

持仓新增走唯一键，更新走版本条件，版本不匹配返回 409，页面保留用户输入并提示重新加载核对。服务端保存时更新确认时间。「确认未变」提交原字段和版本；「标记清仓」先展示二次确认，再提交零股。请求超时后先读取已保存版本供用户核对。新建持仓若遇到身份解析失败，显示具体原因并保留待编辑输入；已登记行可用本地已核验身份维护。

估值取同一证券在 `market_snapshots` 中最近一份已校验快照的有效不复权收盘，按行情日期优先、抓取时间次序读取，标注参考价与交易日。较旧的已校验价格仍可显示为历史参考，缺少可靠报价时市值和盈亏显示「—」。Java 用 `BigDecimal` 计算，金额按人民币展示。

- 参考市值 = 股数 × 不复权收盘。
- 参考浮动盈亏 = 股数 ×（不复权收盘 − 录入成本）。成本缺失时显示「—」，只在成本大于零时展示盈亏百分比。
- 已清仓显示零持有市值，盈亏栏显示「—」。持仓表表达当前快照，已实现盈亏留给后续成交记录需求。

## 3. 提交时冻结，报告时按证券身份绑定

1. `POST /api/v1/analyses` 请求继续只接收 `code` 和 `mode`。提交线程在入队前用一次本地查询捕获持仓记录和读取时间。带后缀按 canonical code 捕获，裸代码按六位代码捕获本机候选记录。候选是只读任务输入；当前服务重启仍将中断任务标记失败，由用户显式重跑。
2. 行情阶段用原有数据校验流程确认 canonical code 后，仅绑定代码完全匹配的已捕获行。身份已确认且捕获时无对应行，标记「未登记」。身份未确认，标记「持仓无法匹配」。持仓读取失败时单独记录「持仓读取失败」，行情和公告可继续生成。持仓被修改或标记清仓后，已排队任务仍使用提交时捕获的记录。
3. Java 将持仓状态、确认状态、动作、理由和下一检查条件写入报告。新增可选 `positionSnapshot`，包含结构版本、读取时间、确认时间、持仓版本、股数、成本、来源、预设动作、规则 ID／版本、判定状态，以及两日行情证据或对应缺口。已知的证据包含交易日、同口径收盘和各自的 MA55，沿用 `sellReview` 的值。
4. `SnapshotRepository.finish` 与现有报告一起保存新增字段并计算报告 hash，终态仍由数据库保护。历史详情读取原快照。旧报告缺少此字段时显示「当时未记录持仓上下文」。若个股页检测到报告对应的记录已新增，或持仓版本与当前记录不同，提示「持仓已更新，请重新生成以查看当前动作」，保留旧报告的时间和证据。

### 首屏状态与动作

行情规则复用 `TechR1.sellReview`。只有质量可靠、符合现有最新终值口径、最近两个交易所开放日各有有效且可比的行情，并且两个收盘都严格低于各自 MA55，才显示「已触发」。等于 MA55 为「未触发」。停牌跳日、口径冲突、终值缺失及不足两日 MA55 均为「数据不足」。MA55 使用既有同口径归一化序列，持仓估值使用不复权收盘，两类价格分别标记。

| 本次持仓上下文 | 价格条件 | 首屏显示 |
| --- | --- | --- |
| 已确认持有 | 已触发，已设动作 | 「进入减仓评估」或「进入退出评估」，附两日收盘与 MA55。 |
| 已确认持有 | 已触发，未设动作 | 「价格风险条件已触发，待补退出规则」，可回持仓页设置。 |
| 已确认持有 | 未触发 | 「MA55 退出条件未触发」，附证据和下一检查时间。 |
| 已确认持有 | 数据不足 | 「暂不能判断 MA55 退出条件」，明确缺少哪一天或哪项校验。 |
| 已确认清仓 | 任一结果 | 「空仓观察」，单列价格信号；符合条件时沿用现有 D+1 观察计划。 |
| 未登记、待确认、匹配或读取失败 | 任一结果 | 「先确认持仓」，按实际原因给出录入、确认或重试入口。已取得的独立价格信号仍显示。 |

首版将「北京时间当天确认」作为使用个人预设动作的默认时效。之前确认的持有或清仓记录仍展示股数、状态及确认时间，动作区提示先确认。该默认值集中在服务端一处，便于试用后调整。下一次检查写成可核对的条件，例如「下一个交易日收盘，待终值入库后检查」。盘中使用最近已完成的交易日终值，盘后从北京时间 18:00 起请求 BaoStock 当日终值及复权数据。首屏区分分析时点、行情基准日和待发布状态。腾讯已确认的当日不复权收盘可先单独展示，持仓动作和技术指标继续使用通过校验的 BaoStock 数据。日期无法确定时，页面写明待取得交易日历或缺少的终值。

## 4. 模型与缓存边界

- **行情缓存**沿用当前按证券、北京时间自然日的可用行情快照。持仓修改后仍可复用当天行情输入，Java 重新计算报告。打开持仓列表只读取已有行情，缺报价可从对应标的发起分析补齐。
- **模型缓存**沿用现有请求内容、模型、提示词和目标接口决定的键。传给模型的是公开公告原文和公开技术指标。新增持仓字段、动作及快照版本只进入本地报告；仅改持仓且公开输入相同时，生产模式复用已校验证据，调试模式按原逻辑生成新摘要。沿用本应用每月 USD 100、无单日上限。
- **存储边界**为本机数据库与只读报告。持仓字段不进入模型请求、模型缓存键、普通请求日志或地址。数据源失败时分别显示技术、公告或持仓的缺口。已核验的其他部分照常提供。

## 5. 开发顺序与验收

| 切片 | 实现 | 验收 |
| --- | --- | --- |
| 1 · 数据与接口 | V4 持仓表、保存与清仓接口、本地行情估值。 | 在临时本机 PostgreSQL 上验证旧库迁移、重启、增改和清仓。并发写入只有匹配版本成功，旧版本返回 409。验证错后缀、缺成本和缺行情。 |
| 2 · 页面与导航 | 独立持仓和分析记录，复用报告展示，按生成日期筛选。 | Playwright 验证桌面与窄屏、按标的跳转、返回恢复位置、刷新历史详情。打开页面和历史的过程中没有提交分析请求。 |
| 3 · 报告与缓存 | 在提交时捕获持仓、按证实的证券身份绑定，生成首屏状态，保存不可变快照。 | 用合成持仓覆盖三个基础状态及待确认、无法匹配、读取失败。用确定性行情向量覆盖触发、等于 MA55、停牌或终值缺失。入队后改仓，验证旧任务用提交时记录、新任务用新记录、旧报告 hash 一致。捕获测试模型请求，验证只改持仓时生产命中且不重发，调试仍发新请求。 |

验收使用隔离数据库和测试持仓。对技术信号与本机隐私边界的验证无需使用真实持仓或付费模型请求。通过三条页面路径、状态矩阵和不可变历史检查后完成本增量。
