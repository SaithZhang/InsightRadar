## 决策摘要

InsightRadar 是一套服务个人 A 股投资者的投资决策智能系统。它不以数据量、信号数量或 Agent 数量作为竞争目标，而是把分散的证据压缩成少量、相关、可审计、带条件的决策与预警，并在事后衡量这些判断的结果。

产品始终以持仓为优先。当用户已经批准当前持仓时，持仓决定信息的相关性与优先级；当没有获批持仓时，产品可以提供一个受控的候选观察池，但不能因此变成泛化的股票发现信息流。

面向用户的产品承诺是：

> 聚合真正重要的信息，理解你的持仓，发现值得观察的机会，提前预警风险，让每次投资决策都有证据、有边界、能复盘。

简短定位语：

> 从分散信息，到清晰决策。

## 北极星

InsightRadar 持续聚合持仓、行情、公告、政策、宏观、国际市场、产业变化与资金行为等证据，识别真正影响用户组合或市场判断的重要变化，并将其转化为来源可追溯的投资指引和关键预警，同时明确条件、风险边界、不确定性和后续跟踪要求。

系统包含两种共享同一证据和验证契约的决策模式：

1. **持仓模式：**解释获批持仓发生了什么变化、有哪些条件化行动、什么情况会使原判断失效，以及下一步需要观察什么。
2. **市场候选模式：**当持仓为空或较少时，提供 0—5 个候选观察标的。每个候选必须明确入选逻辑、触发条件、失效条件、观察周期与主要风险；候选数量为 0 是完全有效的结果。

所有输出都必须保留缺失和过期数据，不进行自动交易，并在对应观察周期成熟后进入结果校准闭环。

## 产品边界

InsightRadar 不是：

- 原始财经新闻信息流；
- 依赖创作者个人魅力的观点订阅或意见复制品；
- 必须每天产生股票的泛化选股器；
- 给出确定买卖答案的预言机器；
- 自动交易系统；
- 由 Agent 不断产生愿望功能的功能市场。

新闻是证据，不是结论。候选标的是观察对象，不是立即买入指令。技术触发不能覆盖缺失的持仓数据、尚未核实的公告或硬性风险否决。

## 核心产品能力

### 1. 信息与事件智能

事件感知层覆盖：

- 用户批准的持仓、成本与风险背景；
- A 股价格、市场宽度、流动性、风格、股指期货基差和市场状态证据；
- 巨潮资讯、交易所和上市公司公告；
- 金十等用于快速发现事件的快讯源；
- 宏观政策、国际市场、利率、汇率、大宗商品和地缘政治事件；
- 行业、供应链、研究、资金流以及机构与 ETF 相关证据。

快讯只是事件发现来源。重要公告与政策信息必须尽可能由最高优先级的一手来源确认。系统需要记录来源、事件发生时间、数据截止时间、新鲜度、核实状态和仍未解决的数据缺口。

### 2. 相关性与影响映射

每个重要事件都遵循同一条处理链：

`发现 -> 核实 -> 分类 -> 映射 -> 评估 -> 决策 -> 复盘`

映射后的事件记录必须回答：

- 哪些信息是新增量，哪些只是累计数据或此前已知信息？
- 影响哪个市场、行业、主题、持仓或候选标的？
- 影响周期属于日内、战术阶段还是投资逻辑层面？
- 正向和负向的传导路径分别是什么？
- 哪些证据能够确认或证伪当前解释？
- 该事件是否改变原计划、风险预算、候选状态，还是不产生实际影响？

例如，快讯提到国家资本“已经使用”的稳市资金时，系统不能把累计金额直接当成下一交易日将新增的等额资金。它可以提高稳市力量、央企核心资产、央企科技、相关 ETF 以及价格与资金确认的观察优先级，但不能单独授权增加仓位。

### 3. 投资指引与关键预警

投资指引必须采用条件化、结论优先的表达。一个达到决策就绪状态的项目需要包含：

- 受影响对象和优先级；
- 带来源和截止时间的事实证据；
- 基础解释以及可信的反向证据；
- 条件化行动或观察要求；
- 触发条件和失效条件；
- 风险边界与时间周期；
- 缺失输入以及置信度或校准状态；
- 下一次复查节点。

只有在事件影响获批持仓、使候选失效、改变市场或风险状态，或者实质性改变此前计划时，系统才将其提升为预警。其他信息留在背景证据中。没有重要变化时保持安静，优于制造低价值预警。

### 4. 候选观察池

候选生成必须服从当前市场状态和组合风险。默认输出为 0—5 个候选，而不是必须完成的数量指标。

每个候选都需要：

- 透明的市场、行业和公司逻辑；
- 带来源且标注新鲜度的证据；
- 明确的观察周期；
- 关注或入场触发条件，而不是无条件买入结论；
- 失效条件和主要风险；
- 在数据可得时提供流动性与执行限制；
- 后续相对基准的结果复盘。

候选在用户采纳之前不会成为持仓行动；未来若建立自动晋升工作流，也必须通过明确且经过审阅的门槛。

### 5. 结果校准

每一项重要指引、预警和已晋升候选，都应进入后续复盘。观察周期成熟后，需要记录样本量、相对基准收益、在原方向定义下的命中或失效、MFE/MAE、回撤与尾部损失、盈亏比、市场状态、数据质量以及用户是否实际执行。

未成熟样本继续保持 `pending`。任何报告都不能根据少量或缺乏代表性的样本宣称已经形成稳定优势或稳定复利能力。

## Alpha Report 是交付产品族

`Alpha Report` 是面向用户的主要交付产品族，但不是北极星本身。同一份产品契约可以通过定时简报、事件驱动预警、仪表盘、历史归档或交互问答呈现，而不改变产品使命。

Alpha Report 产品族需要始终保留：

- 结论优先的摘要；
- 持仓相关性优先于泛市场信息；
- 重要国际、政策、公告和市场结构变化；
- 少量条件化行动或候选标的；
- 关键风险、失效条件和明确数据缺口；
- 证据链接和后续结果记录。

产品在运营上可以存在不同时间版本，但产品价值由决策质量定义，而不是由盘前、盘中或盘后标签定义。

## 逻辑架构

本设计保留现有模块化单体结构以及 Core/Lab/Extension 产品环，不增加服务拆分，也不增加自动交易路径。

| 逻辑单元 | 职责 | 输出契约 |
|---|---|---|
| 证据采集器 | 获取持仓、行情、公告、快讯、宏观、国际市场和研究输入 | 带时间戳、来源和新鲜度的证据 |
| 事件标准化器 | 去重、分类，区分新增事实与累计事实 | 带核实状态的类型化事件记录 |
| 相关性映射器 | 将事件映射到持仓、行业、主题、候选和市场状态 | 影响对象、周期、传导路径与置信度 |
| 决策引擎 | 应用持仓状态、市场状态、风险否决、触发和失效条件 | 条件化指引、预警和候选池 |
| Alpha 交付层 | 渲染结论优先的页面与通知负载 | JSON 及人类可读的报告载体 |
| 结果账本 | 等待观察周期成熟并与基准比较 | 可审计的校准结果和产品指标 |
| 产品治理 | 接纳、拒绝、合并或淘汰产品实验 | 问题队列、验收证据和淘汰决定 |

模块接口保持类型明确并能追溯来源。上游数据源失败时必须降级为明确的数据缺口，不能静默填入虚构数值或模型猜测。

## 失败与不确定性处理

- 风险输入缺失或过期时，对新增风险暴露采取失败关闭。
- 持仓字段缺失时继续保持未知，并阻止严格决策就绪。
- 来源冲突必须保留可见；重要公告以一手来源为优先。
- 快讯文本在完成核实和相关性映射之前不能直接生成行动。
- 数据源超时必须有明确上限，并记录回退状态。
- 低置信度或低相关性事件保留为背景证据。
- 候选生成允许返回空池。
- Agent 发生分歧时，主 Agent 先依据证据契约裁决；涉及重大产品方向或投资政策的选择由用户最终决定。

## 产品指标

第一指标：

- **持仓决策就绪覆盖率：**获批持仓中，具备新鲜相关证据、条件化指引、风险与失效条件，并明确披露数据缺口的比例。

辅助指标：

- 预警准确率、重大事件漏报率和事件到洞察的延迟；
- 能够映射到持仓、已采纳逻辑、候选或明确风险规则的预警比例；
- 候选晋升率和成熟后的相对基准结果；
- 数据源新鲜度、可靠性、回退率和未解决缺口；
- 用户认为有用或采纳的比例，以及节省的研究时间；
- 结果样本量、MFE/MAE、回撤、盈亏比、市场状态稳定性和现实交易成本。

功能数量、报告数量、候选数量、Agent 数量以及单独的胜率都不是成功指标。

## 产品准入门槛

新的 Core 功能必须同时具备：

1. 反复出现的真实用户问题，或一个高严重度失败；
2. 明确属于 `Observe -> Explain -> Decide -> Verify` 闭环中的哪一部分；
3. 开发前基线和可衡量结果；
4. 能够验证问题的最小可用实验；
5. 明确的数据与安全边界；
6. 淘汰或合并条件以及复查日期。

任何时候只能有一个正在进行的产品实验，候选队列最多保留两个。Agent 维护的是问题队列，而不是自动生成的功能愿望池。

## 多 Agent 运作模式

角色是稳定模板，Agent 是临时工位。当任务确实适合并行时，当前运作方式使用一个主 Agent 加最多三个任务 Agent。

| 角色 | 职责 | 权限边界 |
|---|---|---|
| 用户／董事会／首席实践者 | 确定北极星、提供真实纠错、批准重大范围与发布 | 拥有最终产品和投资政策决定权 |
| 主 Agent／CEO-CPO | 汇总证据、管理问题队列、选择一个实验并整合结果 | 未通过产品门槛不能立项 |
| 证据与持仓分析师 | 分析使用轨迹、持仓、结果、数据缺口和重复失败 | 不能独立创建实施范围 |
| 市场与竞品分析师 | 比较市场产品、事件、工作流和 A 股本土证据 | 只读调研和差距分析 |
| 产品反方／删减 Agent | 质疑价值、复杂度、重复建设和虚假确定性 | 默认拒绝、合并、简化或停放 |
| 架构与开发 Agent | 实施已经批准且范围明确的设计 | 不能扩大已批准验收条件 |
| 独立评估 Agent | 检查契约、产物、回放、回归和结果宣称 | 实施者不能决定自己的最终验收 |
| 运维验证 Agent | 检查新鲜度、可观测性、恢复和回滚 | 不能改变产品方向 |

只读探索、测试分类和审查可以并行；对仓库的写入按照明确所有权串行执行。主 Agent 保留完整上下文，专业角色只接收其任务所需的有限证据，以减少成本、重复和角色越界。

运作闭环为：

`真实使用/纠错 -> 结构化轨迹 -> 问题聚类 -> 受门槛约束的方案 -> 用户批准 -> 有界开发 -> 独立验证 -> 影子使用 -> 保留/合并/删除`

## 竞品参考

InsightRadar 吸收不同产品的有效工作流，但不复制任何一个产品：

- **Meet Kevin Alpha Report：**固定的每日使用习惯、隔夜国际背景、最新研究、关键价位和历史归档。借鉴简洁的交付节奏，不借用创作者个人权威或泛化交易指令。
- **Klarion：**围绕持仓的解释、市场异动预警、风险敞口映射和历史相似情形。借鉴“为什么这个事件与当前用户有关”的要求。
- **AlphaSense：**统一、可审计的研究以及定时监控 Agent。借鉴主动证据采集和带来源的综合判断。
- **Koyfin：**针对持仓与观察池的新闻、公告、价格、估值和技术条件预警。借鉴明确的用户相关触发管理。
- **TradingView：**分离历史策略计算和实时预警执行。借鉴可回放的触发语义与评估边界。

InsightRadar 的差异化来自 A 股本土证据、用户批准的真实持仓、明确的市场与风险状态、条件化投资指引、失败关闭的数据缺口和持久化结果闭环。

## 已考虑的替代方案

### 报告优先的创作者产品

不作为北极星。它能够形成较强的每日使用习惯，但依赖单一人格，对用户持仓的个性化和结果校准较弱。

### 信息终端产品

不作为北极星。它可以最大化信息广度，但容易变成另一个把最终决策负担留给用户的仪表盘。

### 自主选股系统

不采用。它会鼓励强行生成候选、隐藏不确定性，并与不自动执行和证据约束的产品契约冲突。

### 持仓优先、受控候选补位的决策智能系统

采用。它保留了明确的初始切入点，也覆盖无持仓场景，并把信息相关性、风险和后续验证变成第一等产品行为。

## 验证策略

从本设计派生的实施计划必须验证：

- 标准化事件的结构和来源追溯契约；
- 面向获批持仓和空持仓场景的相关性映射；
- 重要来源优先级，以及新增事件与累计事件的区分；
- 预警晋升、去重、过期和保持安静的行为；
- 零候选与候选数量上限场景；
- 不产生任何自动交易副作用；
- 受影响报告的 JSON、Markdown 和 HTML 一致性；
- 无未来函数的回放、可见样本量和未成熟周期；
- 真实产物生成、数据缺口披露和项目记忆校验。

本设计允许后续制定实施计划，但它本身不会激活新的实施功能，也不会改变当前 `feat-044` 代码待办。
